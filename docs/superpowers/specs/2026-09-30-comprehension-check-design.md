# comprehension-check: Skill Design

Date: 2026-09-30

## Goal

A Claude Code skill that quizzes the user on code Claude wrote during the current session, to find the parts the user could not maintain themselves. It fills a gap: existing tutor and quiz skills (for example claude-tutor, study-quiz) quiz on study material or topics, not on the user's own session code.

Audience: developers who let Claude write a lot of code and want to avoid shipping code they do not understand.
Success: after a check, the user knows which parts of the change they understand, which are shaky, and which they could not maintain, each with a `file:line` pointer and a next step.

## Decisions (agreed)

- **Name:** `comprehension-check` (plugin and skill).
- **Trigger:** manual only ("quiz me on that", "check my understanding of this change", `/comprehension-check`). It must never auto-fire after changes.
- **Question generation:** risk-first "what if" questions about failure modes, with a "predict the behavior" framing for one or two subtle spots. Not explain-it-back, not trivia.
- **Delivery:** one question at a time. Claude waits for the answer, grades it, then continues. A summary comes at the end.
- **Scope:** the session's changes (`git diff`, `git log`, and the conversation), ranked by risk (concurrency, error paths, state and ordering, security boundaries, non-obvious logic). A user-named file or commit overrides.
- **Form:** one `SKILL.md`, no scripts. No persistence of scores or quiz history (a possible v2).

## Behavior

1. **Scope.** Collect what changed this session. If nothing meaningful changed, say so and stop.
2. **Rank.** Choose the riskiest spots. Question count is 3-5 for a large change, fewer for a small one (a one-line change gets one question or a note that it is too small to quiz).
3. **Quiz.** Ask one concrete failure-mode or behavior question per spot, tied to a specific `file:line`. Never reveal the answer before the user responds. Never ask "what does this function do?". Wait for the answer, then grade: what the user got right, what they missed, and the actual behavior with a code pointer. "I don't know" is a valid answer and counts as a flag, with no lecture.
4. **Summary.** A table of topic, verdict (solid / shaky / couldn't maintain) and `file:line`. List the flagged parts and one suggested next step per flag (for example "ask me to explain X" or "add a test for Y").

If the user asks for the answers without trying, ask for one attempt first, then explain.

Tone: direct and non-patronizing. It is a check, not a grade. No padded praise.

## Grading rule

Before calling an answer right or wrong, Claude must read the relevant code in the current tree. It must not grade from memory or from its own assumptions about the code.

## SKILL.md outline

1. Frontmatter: `name: comprehension-check`; a single-line, double-quoted `description` starting "Use when" and naming the manual trigger (the user asks to be quizzed on, or to check their understanding of, code Claude wrote this session).
2. Overview: the user owns what ships, so test whether they could maintain it, not whether they can recite it.
3. When to use / not use: manual requests only; not for study topics; not for code untouched this session.
4. Process: the four steps above.
5. Question rules with good and bad examples. Good: "If `retry()` throws on the third attempt, what state is `queue` left in?". Bad: "What does `retry()` do?".
6. Grading rules (read the code first; no early answers; "I don't know" is a flag).
7. Common mistakes: trivia, too many questions, leaking answers in the question, quizzing untouched code, padded praise.

## Verification

Behavioral checks, each run with and without the skill (per the writing-skills approach):

| Scenario | Expected with the skill |
|---|---|
| Concurrency-heavy change | Failure-mode questions tied to `file:line` |
| One-line change | One question, or a "too small to quiz" note |
| No changes this session | Stops and says so |
| User answers "idk" | Flagged as a gap, no lecture |
| User asks "just give me the answers" | Asks for one attempt first, then explains |
| Any graded answer | Matches what the code actually does |

Plus `python -m unittest discover -s tests` and `python scripts/validate.py`.

## Out of scope

- Scripts, score persistence, quiz history, spaced repetition.
- Auto-triggering after changes.
- Quizzing on non-session or third-party code.
- Pushing to GitHub is a separate, explicit step.
