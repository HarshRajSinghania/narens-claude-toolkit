# mcp-fixer: the tool-selection benchmark (sub-project 3 of 3)

Date: 2026-10-05

## Purpose

Sub-project 2 can change what a client sees (shorter descriptions, enums, renames). This sub-project measures whether a patch changes how often a model picks the right tool. It generates test tasks from a server's original tool list, runs each task against the original and the patched tool list, and reports both accuracies with a verdict that accounts for sample size. It never claims a patch improves tool selection, only whether a drop was detected.

## Success criteria

1. `mcp-fixer tasks` writes a reviewable, editable tasks file from a server's original tools using a model.
2. `mcp-fixer bench` runs every task on the original and on the patched tool list (built with the wrapper's own `Router`, so it tests what `wrap` serves), scores them, and prints accuracies with 95% intervals, a paired comparison, token sizes, and one of three verdicts: `worse`, `no drop detected` or `inconclusive`.
3. Two interchangeable runners exist (`claude -p`, and the Anthropic API over HTTPS), behind one interface; the test suite calls no real model.
4. The report never overclaims: with fewer than 30 tasks the verdict is at best `inconclusive`, and `no drop detected` is never described as an improvement.
5. The tests pass in CI on Python 3.9 and 3.12 and in the local Windows run.

## Decisions already made

- **Model access:** a runner adapter. `claude -p` first (no API key needed), the API runner behind the same interface.
- **Tasks:** generated by a model from the original tool list only, each request written without naming the tool or copying its description's wording, saved to a JSON file a human can edit; the benchmark runs only from that file.
- **Verdict:** accounts for sample size (Wilson intervals, paired bootstrap), three outcomes, plain numbers always printed too.
- **A trial** shows the model a tool list and one request and asks for `{"tool": "<name>"}`. No tool is ever called, and the runners give the model no tools.
- Standard library only, Python 3.9+, in the existing package `servers/mcp-fixer/` (version 0.3.0).

## Constraints and assumptions

- Accuracy is measured on generated tasks, with one model per run, so it inherits that model's blind spots; the README says so. The `claude` runner runs inside the user's own Claude Code configuration, which can influence replies. A live run against a real server is the owner's.
- The task file, the patch and every model reply are untrusted text. Control characters are escaped in all output (as in the scorer's report). The API key is never printed, logged or written into a report.
- Replies are parsed leniently (clean JSON, fenced JSON, JSON inside prose) but scored strictly: a missing field or a name that is not in the shown tool list is `invalid`, and counts as wrong.
- A runner failure (timeout, nonzero exit, HTTP error) is retried once; a second failure makes the trial `errored`, which is excluded from accuracy and reported as a count.
- Randomness is seeded (`--seed`, default 0): the tool order shown in each trial is shuffled by a seed derived from the task id and repeat number, and is identical for the original and the patched side, so position bias hits both equally.
- The patched list is derived exactly as the wrapper does: `Router` applied to a synthetic `tools/list` response, honoring `base` fingerprints (a stale entry is not applied; the benchmark reports how many entries were applied or stale) and collision rules. A reply naming a renamed tool is mapped back to the original name before scoring.
- `bench` makes `tasks x repeats x 2` model calls. It prints that number (and, for the API runner, a rough input-token estimate) before running, and requires `--yes` above 200 calls.

## The tasks file

JSON, UTF-8, two-space indentation:

```
{
  "tasksVersion": 1,
  "source": {"serverName": "...", "serverVersion": "...", "toolsFingerprint": "<sha256 of the original tool list>"},
  "tasks": [{"id": "t001", "request": "<what the user wants, in plain words>", "expected": "<original tool name>"}]
}
```

- `tasksVersion` (must be 1) and `tasks` (a non-empty list) are required; `source` is optional and informational.
- Each task needs a non-empty string `id` (unique) and `request`, and a string `expected`. Unknown fields are errors. `bench` additionally requires every `expected` to name a tool in the original list (one clear error line naming the task).
- `toolsFingerprint`, when present and different from the current tool list's, makes `bench` print one warning (the tasks were written for different tools) and continue.

## `mcp-fixer tasks`

`mcp-fixer tasks [--tools-json FILE | -- COMMAND ...] [--runner claude|api] [--model M] [--per-tool N] [--out FILE] [--force] [--env KEY=VALUE] [--timeout S]`

- Reads the original tools exactly as `score` and `patch` do (same input modes, same errors).
- Makes one model call per tool (not one for all, so a long list does not dilute attention): the prompt gives the whole tool list for context, names the target tool, and asks for N (default 3) distinct user requests that need that tool and not another, written as a person would say them, without the tool's name and without copying phrases from its description. The reply is a JSON array of strings.
- A tool whose reply cannot be parsed is skipped with one stderr warning naming the tool; a run that yields no tasks at all is an error (exit 2).
- Writes the tasks file to stdout, or to `--out` (never overwrites without `--force`, exclusive create as `patch` does). Ids are `t001`, `t002`, ... in tool order.
- Exit codes: 0, or 2 for usage, input and runner errors (a missing API key is one line before any call).

## `mcp-fixer bench`

`mcp-fixer bench --tasks FILE --patch FILE [--tools-json FILE | -- COMMAND ...] [--runner claude|api] [--model M] [--repeats R] [--tolerance T] [--seed S] [--format text|json] [--out FILE] [--yes] [--env KEY=VALUE] [--timeout S]`

- `--repeats` default 3, `--tolerance` default 0.05, `--seed` default 0, `--format` default text.
- Builds the original list and the patched list, then runs every task x repeat on both sides.
- **The trial prompt** states the tool list (name, description and parameter names and descriptions, rendered compactly from each side's own definitions), then the request, and asks for exactly one JSON object `{"tool": "<name>"}`. The two sides use the identical template.
- **Per side:** `correct`, `wrong`, `invalid`, `errored` counts; accuracy = correct / (correct + wrong + invalid); a 95% Wilson interval; the invalid rate.
- **Paired comparison:** for each task, the per-task accuracy on each side (over scored repeats; a task with no scored repeat on either side is dropped and counted); the difference (patched minus original) averaged over tasks, with a 95% percentile interval from a bootstrap over tasks (2,000 resamples, fixed seed).
- **Token sizes:** the scorer's estimated tokens for each tool list, before and after.
- **Verdict:**
  - `worse`: the upper bound of the paired-difference interval is below 0.
  - `no drop detected`: not `worse`, at least 30 usable tasks, and the lower bound is above minus the tolerance.
  - `inconclusive`: everything else. The report says why (too few tasks, or the interval is too wide) and, when the cause is the interval width, roughly how many tasks it would take at the observed spread.
- The report always prints the plain numbers, the model and runner (`describe()`), the seed, the call counts and the sentence: "This measures whether a drop could be detected on these generated tasks; it does not show the patch improves tool selection."
- `--out` writes the report (text or JSON) to a file; JSON has `schemaVersion: 1`.
- Exit codes: 0 for `no drop detected` and `inconclusive`; 1 for `worse`; 2 for usage and runner errors.

## Runners

All share `complete(prompt) -> str` (raises `RunnerError` with a one-line message) and `describe() -> str`.

- **`ClaudeRunner(model=None, timeout=120)`:** runs `claude -p --tools "" --no-session-persistence` (plus `--model M` when given) with the prompt on stdin; stdout is the reply. These flags exist in the installed CLI (checked with `claude --help`). `--bare` is not used because it skips keychain reads and could break a logged-in session; the consequence is that the user's own Claude Code configuration (CLAUDE.md, hooks, skills) still applies to the call, which the README states as a limit. A missing `claude` executable, a nonzero exit or a timeout is a `RunnerError`; the process tree is stopped on timeout.
- **`ApiRunner(model, api_key, timeout=120)`:** one HTTPS POST to the Messages API using `urllib`, `temperature` 0, a small `max_tokens` (1024 for tasks, 64 for trials), no tools. The key comes from `ANTHROPIC_API_KEY`; it is never included in an error message or report. HTTP and network errors are `RunnerError`.
- **`FakeRunner(function)`:** test double that calls `function(prompt)`.
- The `bench` and `tasks` commands retry a failed call once.

## Testing

Written first, with `unittest`; no test calls a real model.

- **Prompts and parsing:** clean JSON, fenced JSON, JSON in prose, a missing or non-string field, a name not in the list, an empty reply, a reply with several JSON objects (the first valid one wins), an array of strings for tasks, non-string items dropped; a generated-task check helper flags a request containing the tool's name.
- **Stats:** Wilson against known values (including 0 and all correct, and 0 total); bootstrap determinism per seed and a hand-computed small case; verdict boundaries at 29 and 30 tasks, at exactly the tolerance, an obviously worse case, an obviously equal case, and the inconclusive explanations.
- **Orchestration with `FakeRunner`:** always-right runner gives no drop on both sides; a runner that fails on the patched list gives `worse`; renames are mapped back before scoring; a runner that answers with the new name for a renamed tool scores correct; the shuffle is seeded and identical for both sides; invalid and errored trials are counted and not mixed; a stale patch entry is reported and not applied; the call count and `--yes` guard.
- **Runners:** `ClaudeRunner` against a stand-in executable (success, nonzero exit, timeout with the process tree stopped, huge output); `ApiRunner` against a local `http.server` (success, 401, 500, malformed body, slow body timeout, the key absent from every error); a missing key is a clear error before any call.
- **CLI:** exit codes, `--force`, `--out`, the `--yes` guard, the same input errors as `patch`, and that bad tasks files give one-line errors.
- **Safety:** control characters in a request, a tool description or a reply are escaped in the report; a very long reply is truncated in the report; the API key never appears in output.

## Repo integration

- The existing CI job already runs this folder's tests on Python 3.9 and 3.12.
- `README.md` of the server gains `tasks` and `bench` usage, an example report, the verdict rules, and the honest limits (generated tasks, one model, one run, no proof of improvement).

## Out of scope

Calling real tools, scoring argument correctness, multi-turn flows, providers other than `claude -p` and the Anthropic API, sampling-parameter control for `claude -p`, caching of trial results, and publishing to PyPI.
