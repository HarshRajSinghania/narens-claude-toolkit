# Schedule Doctor: design

Date: 2026-10-04

## Purpose

A free skill, `schedule-doctor`, that makes Claude scheduled tasks actually run. It has two halves:

- **Pre-flight**, before a task is scheduled: lint the task prompt, list the tools it will likely need so they can be pre-approved, supply a time guard so a late catch-up run does not act on stale data, and check the machine's sleep settings.
- **Post-mortem**, after a run: classify why a run did not fire or halted, from the run record, without guessing.

It targets all three scheduling surfaces: Claude Desktop scheduled tasks, Claude Code session crons (`/loop`, `CronCreate`), and cloud routines (`/schedule`). The pre-flight is shared; the post-mortem fetch steps differ per surface.

## Success criteria

Each of three known failure modes is detected or prevented, with evidence from real task state:

1. A task halts on a tool nobody pre-approved.
2. A run is skipped because the computer slept (closing the lid still sleeps it).
3. After a missed run, one catch-up run lands hours late and acts on stale data.

## Constraints and assumptions

- The three failure modes come from a write-up tested 2026-09-27 on Claude Desktop 1.1.5368 and Claude Code 2.1.282. They have not been re-verified against the current app. The Desktop app changes quickly, so the skill must stay useful if a release fixes some of them (the shared pre-flight does).
- Task state is **not** reliably readable from disk. On the author's machine no Desktop task store was found; the only on-disk trace of Claude Code crons is a per-project `.claude/scheduled_tasks.lock` (a live-session lock, not a task list), and cloud routines are server-side. The skill therefore reads task state through the scheduling tools, and scripts operate on records handed to them.
- Python 3, standard library only, matching `subagent-tax-auditor`.
- No real failed runs exist yet. Test fixtures are hand-made and labelled synthetic.

## Layout

Scaffolded with `python scripts/new_skill.py schedule-doctor "Use when ..."`:

```
plugins/schedule-doctor/
  .claude-plugin/plugin.json
  README.md
  skills/schedule-doctor/

tests/
  test_diagnose.py
  test_preflight.py
  test_power_check.py
  fixtures/schedule_doctor/   (records/ and power/; synthetic unless named _real)
```

The README catalog is regenerated by `build_catalog.py`, never edited by hand.

## Components

### `preflight.py`

`preflight.py --prompt-file F [--json]`. Read-only. Reports:

- **Likely tools.** Patterns for shell commands, file writes, web access, git push and MCP tool names. Each is marked "pre-approve" or "approve once with Run now". The output says "likely needs", never "will need": it is a heuristic.
- **Time guard.** Whether the prompt already contains one. If not, emits a paste-ready snippet ("if it is more than N hours past the scheduled time, stop and report instead of acting"). N is supplied by the user via the agent.
- **Staleness hints.** Phrases such as "latest", "today", "yesterday" that make a late run act on the wrong date.
- A prompt larger than 20,000 characters is refused with a one-line error (a scheduled prompt that size is a mistake, and the bounded patterns are only fast on small input).

### `power_check.py`

`power_check.py [--json]`. Read-only. Runs `powercfg /query` on Windows or `pmset -g` on macOS and reports the sleep timeout and lid-close action. It states plainly that it cannot see Desktop's Keep awake toggle, so the agent asks the user to confirm that setting. Parsing is a separate pure function so it can be tested against captured output strings.

### `diagnose.py`

`diagnose.py --record F [--json]`. Read-only. Input is a normalized record the agent builds from the surface's tools:

```json
{
  "surface": "desktop | code-cron | routine",
  "scheduled_for": "ISO-8601",
  "started_at": "ISO-8601 | null",
  "ended_at": "ISO-8601 | null",
  "status": "string | null",
  "last_event": "string | null",
  "error_text": "string | null",
  "permission_denied_tool": "string | null",
  "machine_events": [{"kind": "sleep | wake | lid-close", "at": "ISO-8601"}]
}
```

Fields a surface does not provide are `null`. Output is one verdict with the evidence fields it used:

| Verdict | Condition |
| --- | --- |
| `permission-halt` | A permission or tool-denied event ended the run. |
| `slept-through` | No start, and a sleep or lid event covers `scheduled_for`. |
| `late-catchup` | Started later than the late threshold after `scheduled_for`. |
| `never-ran-unknown` | No start and no sleep evidence. Says "not enough data"; does not guess. |
| `healthy` | Started on time and ended without a halt. |
| `failed-unknown` | Started on time and ended with an error text or a failed status that is not a permission halt. The error text is shown (first 200 characters). |

The late threshold is a named constant (default 30 minutes) and is printed in the output. `slept-through` is only returned when there is evidence.

## Process (SKILL.md)

- **Pre-flight:** get the prompt (or read the task through the surface's tool), run `preflight.py` and `power_check.py`, show the tool list and the guard snippet, and ask the user to confirm Keep awake. Adding a guard is a prompt edit: show the diff and get an explicit yes first.
- **Post-mortem:** fetch the task and run record through the tool for that surface, normalize it to the record above, run `diagnose.py`, and report its verdict and evidence verbatim.
- A short table gives the fetch steps per surface. If a tool is not available, say so and stop.

## Rules

- Scripts decide; the agent never names a cause itself. `never-ran-unknown` is reported as unknown.
- Never edit a scheduled task without showing the diff and getting an explicit yes in the conversation.
- Never print prompt or transcript content beyond the matched snippets.
- Do arithmetic and time comparisons only through the scripts.

## Error handling

Malformed or missing JSON, an unreadable prompt file, an unparseable timestamp, and an unsupported OS each produce a one-line error and a non-zero exit, with no traceback. `power_check.py` on an unsupported OS says so rather than guessing.

## Testing

- `diagnose.py`: one fixture per verdict (permission halt, slept-through, late catch-up, healthy, failed-unknown, never-ran-unknown), plus malformed input.
- `preflight.py`: tool detection, guard present and absent, staleness phrases.
- `power_check.py`: parsing against captured `powercfg` and `pmset` sample strings, not the live machine.
- CI is unchanged: `python -m unittest discover -s tests -v` and `python scripts/validate.py`.

## Out of scope

- Reading any app's task store from disk.
- Auto-editing tasks, running or retrying tasks.
- Tracking Desktop app versions.
